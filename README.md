# Isothrum desktop

The Isothrum editor in a window, plus what a browser can't do: **run a lab on this machine**,
**open a console** on its machines, **start, stop and snapshot** them, and **capture traffic**.

- **The editor is bundled** (`editor/`, built from the website by `npm run editor`): the app
  works offline. Accounts and saved projects live on isothrum.com: set
  `ISOTHRUM_URL=https://www.isothrum.com/en` to use the site in the window instead.
- **Run / Stop**: the lab's `isoloom.yml` and its Docker Compose files (generated by Isoloom's
  library, no CLI needed) are written to the app's data folder, then `docker compose up`.
  A lab with VMs runs with **Vagrant** instead: Isoloom's Vagrant output, every machine a VM (a
  container machine in the VM form its OS or its service gives it; a plain image has none, so a
  lab mixing one with a VM-only machine doesn't run). The lab's own files (provisioning scripts,
  appliance configurations) are written next to it.
- **Console**: a terminal on a machine: a shell in its container, SSH to a Cisco appliance's
  management address (`admin`/`admin`, from a helper container on that network), or `vagrant ssh` to a VM. The terminal is `$TERMINAL`, else GNOME
  Terminal, Konsole, Xfce Terminal, Alacritty, `x-terminal-emulator` or xterm (Terminal.app on
  macOS, cmd on Windows).
- **Screen (VNC)**: what a machine shows, in a viewer here, as GNS3's VNC console. A container whose
  image runs a VNC server (it exposes a port in 5900–5999) is reached through a forwarder container
  publishing it on 127.0.0.1 (container addresses aren't reachable from the host under Docker
  Desktop), opened as `vnc://` (Screen Sharing on macOS); a VirtualBox VM opens its own screen
  window, a libvirt VM its VNC or SPICE display. Stopping the lab removes the forwarders.
- **In the editor**, as in GNS3: double-click a running machine for its console, right-click it
  for its console, its screen, and starting, stopping or restarting it.
- **Start, stop, restart** one machine, with its network sidecar (its routes come back).
- **Auto-start**: a lab set to it (in the Run window) starts when the app opens on it, unless it is
  running already.
- **Live status**: while the lab runs, each machine shows its state on the canvas (a dot: running,
  starting, unhealthy, stopped; with its health when its image has a check), each cable whether it
  carries traffic, is suspended or down, and each LAN how many of its ports are up. The ports are
  read from the machines every few seconds: one throwaway container (`nsenter`, privileged, in
  the host's PID namespace) lists each running machine's links. A lab with VMs isn't probed: its
  ports follow the machines' states and the suspended links.
- **Suspend / resume a link**: a cable's ends (or every link of a LAN) set down in the machines'
  network namespaces, as pulling the cable would, and up again with their routes (the machine's
  routes sidecar restarted; a VM's `routes` provisioner run again). A cut link stays cut through
  a restart of the machine, or of the lab, until the lab stops. A Cisco appliance's own port
  can't be cut (its OS owns the address): a cable to one is cut at its other end.
- **Snapshots**: a container saved as an image (`docker commit`: its files, a router's saved
  configuration; not named volumes), restored by running the machine from it; a VM's are
  Vagrant's (`vagrant snapshot`).
- **Capture traffic** on a LAN or a cable: a throwaway container (`nicolaka/netshoot`) joins
  the network namespace of a machine on that segment, finds the interface by its address, and
  streams `tcpdump` live into Wireshark, or into a `.pcap` file when Wireshark isn't installed.
  In a lab of VMs, `tcpdump` runs in a VM on the segment over `vagrant ssh` (installed if
  missing).
- **Updates**: the app checks GitHub's latest release (signed with the app's update key) and
  offers to restart on a newer one.

The editor shows these controls only when it finds the app's bridge (`window.__TAURI__`). Only
the bundled editor and isothrum.com may call the app's commands (`src-tauri/capabilities/editor.json`);
debug builds also allow `http://localhost` for a local build of the site (`src-tauri/src/capabilities.rs`).

## Needs

Docker, usable by your account (Linux: `sudo usermod -aG docker $USER`, then log in again).
For labs with VMs, Vagrant with VirtualBox or libvirt (`vagrant-libvirt`).
Wireshark, to watch captures live.
The app finds them on the PATH, and also in their usual folders when the PATH doesn't say: on
macOS `/usr/local/bin`, `/opt/homebrew/bin` and Docker's and Wireshark's app bundles (an app
started from Finder gets a minimal PATH), on Windows `Program Files\Wireshark`.

## Develop

```
npm install
npm run editor                                       # the bundled editor, from ../../../isothrum-website
                                                     # (or ISOTHRUM_WEBSITE=/path/to/isothrum-website)
npm run dev                                          # the app on the bundled editor
ISOTHRUM_URL=http://localhost:3000/en npm run dev    # against a local build of the website
npm run check                                        # the editor, rustfmt, clippy and the tests: what CI runs
npm run check -- --only clippy,test                  # some of its steps (--list names them)
sg docker -c "npm run check:real"                    # the tests that need Docker (and Vagrant)
npm run build                                        # .deb / AppImage / .dmg / .msi
```

CI runs the check and nothing else: `ci.yml` on pull requests into `dev`, `gate.yml` before `main`
and before a release (`release.yml` builds nothing unless it passes), each on Linux, macOS and
Windows. The tests that need Docker or Vagrant run on the maintainers' test machines.

## Tests

- **Where**: a module's tests are at the bottom of its own file, in `#[cfg(test)] mod tests`, and
  test that file's functions: what `runner/links.rs` does is tested in `runner/links.rs`. The
  editor's commands are tested in `commands.rs`, where their bodies are, as functions of the
  app's data folder: `lib.rs` only finds that folder and runs them off the window's thread.
- **Shared helpers** are in `src-tauri/src/test_support.rs` (built for tests only): `TempDir` (a
  folder of the test's own, removed when it ends), `LabYaml` (an isoloom.yml from networks and
  machines), `Started` (a lab started, and stopped when the test ends, even failing),
  `eventually` (poll a check to a deadline) and `FakePrograms` (stand-ins for `ip`, `tcpdump`,
  `nsenter`..., which answer what the test gives them and record how they were called).
- **Names**: a test's name is the behaviour it proves, as a sentence (`a_new_capture_of_a_network_stops_the_old_one`).
  Cases of one behaviour are one test over a table, not one test each.
- **What is asserted**: values, error variants (`RunError::UnknownAction { .. }`) and parsed
  output, not the words of a message or substrings of a script: a script the app runs in a
  machine is run by `sh` against `FakePrograms`, and what they were asked is checked.
- **Docker and Vagrant**: a test that needs them is `#[ignore = "needs Docker"]` (or
  `"needs Vagrant"`), run by `npm run check:real`, not by CI. Such a test waits by polling to a
  deadline (`eventually`), never by a fixed sleep.

## Release

Push a tag (`git tag v1.1.0 && git push origin v1.1.0`): `.github/workflows/release.yml` builds
the installers for Linux, macOS (Apple Silicon and Intel) and Windows on a **draft** release, with
`latest.json` for the updater, SBOMs, signed checksums and attestations. Publish the draft when it
looks right. [RELEASE.md](RELEASE.md) says what it signs and the secrets it needs.

## Verify a download

Each release carries, beside the installers:

| File | What it is |
| --- | --- |
| `SHA256SUMS` | The SHA-256 of every file of the release |
| `SHA256SUMS.sigstore.json` | A keyless Sigstore signature of `SHA256SUMS` (a cosign bundle) |
| `isothrum-desktop-rust.cdx.json`, `isothrum-desktop-npm.cdx.json` | CycloneDX SBOMs of the Rust crates and the npm packages the app is built from |
| `*.sig`, `latest.json` | The in-app updater's signatures (minisign) and manifest |

GitHub also keeps, for every file, a build provenance attestation (built by this repository's
release workflow from a given commit) and, for every installer, an attestation of each SBOM. The
checks need [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) (step 1) and
the [GitHub CLI](https://cli.github.com/) (steps 3 and 4).

```sh
VERSION=X.Y.Z
BASE="https://github.com/Isothrum/isothrum-desktop/releases/download/v${VERSION}"
curl -fsSLO "${BASE}/SHA256SUMS"
curl -fsSLO "${BASE}/SHA256SUMS.sigstore.json"

# 1. The checksums are the release workflow's, for that tag ("Verified OK").
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
  --certificate-identity "https://github.com/Isothrum/isothrum-desktop/.github/workflows/release.yml@refs/tags/v${VERSION}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# 2. Your download is in them (macOS: shasum -a 256 --ignore-missing -c SHA256SUMS).
sha256sum --ignore-missing -c SHA256SUMS

# 3. It was built by the release workflow.
gh attestation verify <installer> --repo Isothrum/isothrum-desktop \
  --signer-workflow Isothrum/isothrum-desktop/.github/workflows/release.yml

# 4. What it is built from: the SBOMs attested of it.
gh attestation verify <installer> --repo Isothrum/isothrum-desktop --predicate-type https://cyclonedx.org/bom
```

On Windows, compare `(Get-FileHash .\<installer>).Hash.ToLower()` with the installer's line in
`SHA256SUMS`, and check the installer's signature with `Get-AuthenticodeSignature`. On macOS,
`spctl -a -vvv /Applications/Isothrum.app` checks the app's Developer ID signature and
notarization.

A local *production* build of the website served over http needs `LOCAL_HTTP=1` at build time:
WebKit doesn't exempt localhost from `upgrade-insecure-requests`.
